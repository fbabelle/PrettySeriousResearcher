# Repo conventions (standing rules)

Detailed reference for `research-repo-hygiene`. These are the user's working agreements for any research-paper repo. The SKILL.md summarizes; this file is the full spec.

## Directory layout

```
<project-root>/
├── .claude/skills/            # the research-paper skill system (this)
├── README.md                  # quickstart / user manual — how to run code & rebuild figures
├── architecture.md            # designs, workflows, and the project charter (topic, direction, scope)
├── memory.md                  # UNTRACKED — user-behaviour patterns (see below)
├── .gitignore
├── pyproject.toml             # uv project (lazy: with first code) — requires-python >=3.12
├── uv.lock                    # locked dependencies — TRACKED (lazy: with first code)
├── .python-version            # pins 3.12 — TRACKED
├── docs/
│   ├── plans/                 # timestamped plan backups: plan-YYYYMMDD-HHMMSS.md
│   ├── changelogs.md          # append-only log of all changes
│   ├── tracking/              # effort.jsonl, state.json, cost.json (committed); .session (ignored)
│   ├── local-env.md           # probed host: hardware, OS, supplier rate limits (lazy: Phase 3) — see research-experiments
│   ├── claims-ledger.md       # claim → evidence rows, n/seeds/caveat/status (lazy: Phase 3) — see research-provenance
│   ├── venue-profile.md       # early venue-as-input profile (lazy: Phase 1) — see research-venue-selection
│   ├── venues.md              # late deadline-feasible venue plan (lazy: Phase 3/4)
│   ├── review/                # pre-submission research-mock-review packets (lazy: Phase 4)
│   └── submission/            # staged portal forms, response drafts (lazy: at submission) — see research-submission
├── drafts/                    # versioned paper drafts: vNN-title.md; _archive/ is ignored
├── src/                       # method/solution implementation (lazy: created in Phase 2)
├── experiments/               # experiment & ablation harness (lazy: Phase 3)
├── runs/                      # run outputs incl. usage.jsonl (lazy: Phase 3)
├── figures/                   # figures-as-code: src/ (committed) + out/ (generated, gitignored) — see research-visuals
└── tests/                     # unit/regression tests (lazy: with first code)
```

Cross-cutting infra (`docs/`, ledgers, `README.md`, `architecture.md`, `.gitignore`, `memory.md`) is created **up front** on first engagement. Code/experiment dirs are created **lazily** when their phase reaches them — don't commit empty skeletons that imply structure not yet designed.

## docs/plans/ — plan backups

Every significant AI-agent plan is backed up here with a timestamp trailing the filename (`plan-YYYYMMDD-HHMMSS.md`) before execution. This preserves the planning trail. Backing up a plan is also the trigger to **re-run `research-tracking`** and report the effort+cost line.

## docs/changelogs.md — change register

Append-only. Every change gets a dated entry: what changed and why (feature/fix/decision), not effort hours. Reflection outcomes (from `research-reflection`) are logged here too.

## drafts/ — versioned paper drafts

- Drafts are **md + pdf pairs**: `vNN-title.md` (source of truth) plus a compiled `vNN-title.pdf`, kept in sync. The Phase-1 skeleton is `v01`. PDF compilation + typography rules live in `research-writing` (pandoc + LaTeX engine; render math/tables/citations faithfully; follow the venue template).
- **Start a NEW draft when a chunk of effort exceeds ~5 agent-active hours** (measured per `research-tracking`), rather than editing the old in place — this preserves the trajectory of major revisions.
- **Periodically untrack superseded drafts:** move the whole pair (`.md` + `.pdf`) to `drafts/_archive/` (gitignored) so the repo stays lean while the history survives in git.

## README.md & architecture.md

- `README.md` — quickstart / user manual: how to set up, run the code and experiments, and rebuild the figures. Updated less often, but should be accurate by submission.
- `architecture.md` — the design/workflow doc **and** the project charter (topic, chosen direction, scope, success criteria from Phase 1). Updated less often; keep it reflecting the current design.
- Be aware these exist and update them regularly even though they change infrequently.

## Commits, push, and PRs

- **Commit by feature/functionality, not by effort/hours.** A commit captures a coherent unit of work.
- **When the user changes subject, commit the previous chunk** — that's the natural boundary.
- **Push automatically** after committing.
- **PR to remote main only when the user explicitly requests it.** Never auto-merge to main.
- **No co-author / "generated by" footer** on commit or PR messages — write them as normally authored.
- If this project lives inside a larger monorepo (rather than its own repo), use a feature branch namespaced like `research/<paper-slug>/<feature>` rather than committing research work straight onto the shared default branch.

## Tests

- Unit/regression tests ship **with** all new code and core designs.
- Tests are **tracked and committed** — they're part of the repo.
- After major changes, the suite must **pass** before the work is considered done.

## Python environment (uv)

All Python for the paper is managed by **`uv`**, for reproducible, locked environments.

- **One uv project per repo.** Maintain a committed `pyproject.toml` (project metadata + dependencies) and a committed **`uv.lock`** (the resolved, pinned lockfile — tracked so runs are reproducible across machines). Initialize with `uv init` when the first code lands (Phase 2); it's a lazy artifact like `src/`.
- **Python 3.12 by default.** Pin it: `.python-version` containing `3.12` (tracked) and `requires-python = ">=3.12"` in `pyproject.toml`. Use `uv python pin 3.12` to set it.
- **Add deps with `uv add <pkg>`** (never hand-edit installs) so `pyproject.toml` + `uv.lock` stay in sync; `uv sync` reproduces the env from the lock.
- **Run everything through uv:** `uv run python <script>` / `uv run pytest`. The env lives in `.venv/` (created by `uv venv` / `uv run`, **gitignored**). Don't invoke a bare system `python` for project code, and don't `pip install` into a global env.
- **Commit discipline:** `pyproject.toml` and `uv.lock` are tracked and committed together whenever dependencies change; `.venv/` is never committed.
- **Carve-out — skill tooling stays dependency-free.** The skill set's own `track.py` is stdlib-only and may run under plain `python3` so effort/cost tracking works in Phase 1 *before* a uv project exists (inside a set-up project, `uv run python …/track.py` is equally fine). This carve-out is **only** for the dependency-free skill utilities — all code *you write for the paper* uses uv.

## memory.md — user-behaviour patterns (UNTRACKED)

- Records patterns in *this user's* behaviour (commands, preferences, recurring requests, corrections), summarized from past interactions.
- **Structure** (skill-file-like): a rolling **summary of the user** at the top (updated as new specifics accrue), then a `---` mark, then dated changelog-style **specific entries** below.
- **Not tracked in the repo** (it's user-specific) — keep it in `.gitignore`.
- **Priority:** if any item here contradicts a project-scope skill file, the skill wins on *methodology / how-to*. `memory.md` wins on the user's *explicit stated choices/preferences*. The "demote on contradiction" rule applies to stale or accidental entries, not to legitimate preferences.

## Source vs install — don't self-edit the skills

This skill set is **authored in its source project and installed read-only into paper projects.** While building a *paper*, treat `.claude/skills/**` as immutable tooling: don't edit a skill to fix or extend it mid-paper — that silently diverges the installed copy from source, and the next reinstall (to pull updates) will clobber or conflict with the edit. If a skill is wrong or missing something, note it and fix it **upstream in the source project**, then reinstall. Authoring/maintaining the skills (the `name`/`description` limits, SKILL.md best practices) is a source-project task and is documented there, not here.
